# 贡献指南

欢迎通过 Issue 和 Pull Request 一起维护项目。开始前请阅读 [agents.md](agents.md) 和 [PRD](docs/PRD.md)。

## 提出 Issue

- 缺陷：写清操作步骤、实际结果、期望结果和设备／浏览器。区分页面骨架尚未实现的能力与已实现功能中的错误。
- 功能建议：描述用户、使用场景、问题及期望结果，注明是否涉及既有 PRD 取舍。
- 需要跨多个功能的大改动，先通过 Issue 对齐范围，避免直接重写产品方向。
- 不上传真实用户隐私、凭据或未经授权的商品素材；截图须去除敏感内容。

## 提交 Pull Request

1. Fork 本仓库，在 Fork 中创建说明用途的功能分支。
2. 一次 PR 聚焦一个问题，保留原有需求与用户修改。
3. 改动需求、架构、文件结构或实现进度时，同步更新 `agents.md` 及相关文档。
4. 运行适合本次改动的检查，如实说明验证范围。当前缺少 `app.js`，不要声称整套应用已经通过验证。
5. 提交到上游 `main`，填写 PR 模板，说明问题、变化、验证与限制。
6. 等待仓库所有者评审。根据意见修改后，新提交需要重新评审。

## 合并与权限

- 外部贡献者通过 Fork 提交，不默认分配写入、维护或管理权限。
- `main` 计划启用分支保护，并要求至少一项批准及指定代码所有者评审；实际启用状态见 [仓库协作说明](docs/github-collaboration.md)。
- 仓库所有者是所有文件的指定评审人，最终决定是否合并。
- 管理员可能具备绕过保护的权限。保持“所有者批准”的治理要求时，不向其他人或自动化服务授予管理员权限，不启用自动合并。
- 工作流通过不代替所有者批准，申请修改协作规则也必须经过同样评审。

## 开发约定

- 文件使用 UTF-8，尽量保持改动简洁，不引入不必要依赖。
- 不提交 `.env`、令牌、私钥、用户上传图片、本地缓存或构建归档。
- 生成必须绑定已批准的素材与方案版本；变更后不能沿用失效批准。
- 不将占位图、规则回复或构图预览标为真实 AI 输出。
- 不在未经过素材验证时承诺商品完全保真或平台全适配。
- 第三方代码、图片与字体必须核对授权；本仓库自身许可尚待所有者决定。
