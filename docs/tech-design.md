## 2. 总体结构

```text
浏览器（界面＋本地数据）                          服务端（Next.js 接口，只做代理）            AIHubMix
┌───────────────────────────────┐   POST /api/chat     ┌──────────────────────────┐   对话模型
│ 页面：首页／作品／工作区／风格／布景／历史 │ ───────────────────▶ │ 小间：streamText＋工具定义  │ ─────────▶
│ 工作区：左对话（useChat）右画布      │ ◀─── 流式回复＋工具调用 │ 记账：按 token 计费        │
│ 工具执行器：小间的工具在浏览器里执行   │                      └──────────────────────────┘
│ 规则层：批准、快照、状态机（纯函数）   │   POST /api/images   ┌──────────────────────────┐   生图模型
│ 存储：IndexedDB（作品、图片、对话）    │ ───────────────────▶ │ 提交任务、查询、下载        │ ─────────▶
└───────────────────────────────┘ ◀─── 任务状态／图片   │ 预算与重试上限检查          │
                                                     └──────────────────────────┘
```

- **数据都在浏览器**（PRD O5）。服务端不存作品和照片，只转发请求，并记一本花费账。
- **密钥只在服务端**：现在是 `正式代码/.env.local` 里的 `AIHUBMIX_API_KEY`，不进版本库，也不发给浏览器。v0.5：服务器上改由管理后台录入、加密存文件，协作者经服务器转发（第 12 节，已实现，未部署）。
- **小间的工具在浏览器执行**：模型决定调用哪个工具，工具的执行代码在浏览器里运行并修改本地数据。这样服务端不需要保存作品状态。
- **不设访问限制**（2026-10-31 发起人决定）：试用网址不加邀请码或密码，发起人判断不会有外人使用；花费由服务端的预算上限兜底。
- **硬规则的保证范围**：批准与生成前的检查在浏览器的规则层和工具执行器里做，能挡住模型绕过规则；服务端不存作品，无法校验批准，只负责预算和重试上限。改浏览器代码的人挡不住，试用期可接受。
- **花费按作品记录**：服务端每次调用算出花费，随响应返回；浏览器记在对应的生成任务和对话上，试用记录据此统计每人累计成本（PRD 6.2 记录模板）。做法：生图花费记在任务上并累加进 `work.costUSD`；对话请求开始时元数据 `costUSD` 置 0、结束时写本次花费，浏览器在 `useChat` 的 `onFinish` 里（排除中止和出错）加进作品。中止或出错的对话不累加，服务端账本仍按估价记全，总预算不受影响。

## 4. 数据模型（IndexedDB）

| 表 | 内容 | 关键字段 |
| --- | --- | --- |
| `works` | 作品 | 名称、创建／更新时间、商品信息、共创、风格卡、比例、所选生图模型与对话模型、资产路线 A/B、选用的白底图、提示词、最近一次批准、累计花费、正在从哪张结果修改（`revision`） |
| `assets` | 商品照片与派生图 | 所属作品、类型（整体／背面／细节）、来源（上传／白底，白底图记父图和做法 `generate`／`matting`）、是否停用、被哪张替换 |
| `blobs` | 图片二进制 | 原图、缩略图、白底图、生成图都存这里，其他表只存编号 |
| `messages` | 对话 | 所属作品、AI SDK 的 UI 消息原样保存（含工具调用记录，满足 AC-11.4） |
| `approvals` | 批准记录 | 所属作品、第几版、快照（参考图、路线、核心信息、总结、风格、布景、比例、生图模型、提示词、张数）、用于第几轮、父结果 |
| `tasks` | 生成任务 | 所属作品、类型（场景图／白底图）、所用批准、第几轮第几张第几次、模型、状态、网关任务编号、账本编号、估算花费、失败原因、父结果 |
| `results` | 候选图 | 所属任务与批准、第几轮第几张、图片、父结果、还原度与风格两项验收、问题标签、说明、导出记录 |
| `scenes` | 摄影布景 | 名称、背景、光线、道具、布局、版本历史 |
| `shopStyle` | 我的风格 | 长期偏好、变更记录（每次变更都由用户同意） |
| `events` | 试用事件 | 时间、类型、所属作品、少量数字或短文本（不存整段聊天和原图，AC-10.4） |

关键规则：

- **商品信息每个字段带状态**：已确认／待确认建议／未知。小间写入的只能是「待确认建议」（PRD 4.2 第 3 条）。
- **共创总结带状态**：草稿／已确认。小间只能写草稿，确认由用户点。
- **原图不可覆盖**：替换原图是新增一条记录，旧记录保留（PRD 4.2 第 5 条）。
- 数据表带版本号，以后改结构用 Dexie 的升级函数迁移，不丢旧数据。只加不建索引的可选字段（如 2026-11-01 加的 `revision`、`parentResultId`）不需要升级版本，读的时候把缺省当作没有。
- 修改结果（验收、问题标签、说明、导出记录）用 `patchResult` 按数据库里的最新记录只改对应字段，连着点也不会互相覆盖。
- 2026-11-01 新加的可选字段（不建索引，不升级版本）：作品 `followups`（记下的后续需求）、`proposals`（提议卡片上用户的决定，按工具调用编号）；结果 `thumbId`（缩略图，早期结果没有就用原图）、`published`（商家说已经拿去发布的时间）；任务 `whiteAssetId`（白底任务存下的白底图）。
- 2026-11-06 新加的可选字段：风格卡每项的 `quote`（来源为「你说的」时，代码核对过的用户原话片段）。房间参考没有新字段，直接用批准记录里已有的父结果 `parentResultId`（v0.6 取消房间参考，见第 13.5 节）。

## 5. 方案、提示词与批准（核心规则）

按发起人决定（PRD AC-07.2a），**最终提示词全部由小间撰写**：

1. **提示词依据**：商品信息（已确认部分）、共创总结（已确认）、风格卡、比例、生图模型、所选资产。代码对这些内容算一个「依据指纹」。
2. **小间写提示词**：调用 `draft_prompt` 工具，写入提示词原文和当时的依据指纹。系统指令要求它写清：主体描述、不能改的细节、只保留原图看得到的结构（不加扣头和链条）、完整入框留边距、无文字，再加上氛围描写。
3. **过期**：当前依据指纹和提示词记录的不一致时，界面标「提示词可能过期」，批准按钮不可用，小间会主动提出重写；用户也可以对照改动后点「我核对过，仍然适用」，依据更新为当前（小间不可用时也能继续，AC-11.6）。
4. **用户可以直接改提示词**（同步做法 2026-10-31 确认，落实 AC-07.2）：改后标「已手动修改」，状态记为「未核对」，小间读一遍改动：
   - 能对应到方案卡的写回方案卡；写回后把提示词记录的依据指纹更新为新状态，避免把用户刚改的提示词判成过期。
   - 对不上的列为「待你决定」，状态记为「有矛盾」。
   - 「未核对」「有矛盾」时批准按钮不可用（由代码判断）。小间同步失败或不可用时如实提示；用户可在画布上并排核对方案与提示词后手动标「已核对」，或撤销手改（AC-11.6：没有模型也能完成确认）。
5. **批准**：只能由界面上的「批准」操作产生（滑动确认组件）。批准记录保存一份快照：资产编号、路线、商品信息、共创总结、风格卡、比例、生图模型、提示词原文、候选数量 2。
6. **批准是否有效**：当前快照与批准快照逐项比对，任一项不同即失效，并列出改了哪几项（参照 v2 原型 `snapshotOf`、`diffSnapshot`）。
7. **生成**：只有存在有效批准才能提交；提交时带上批准编号，按快照里的提示词和资产生成。生成中锁定方案：风格、布景、比例、提示词、生图模型、商品核心信息、共创总结、资产都不能改（画布禁用，小间相应工具拒绝）；售价、目标顾客不在快照里，随时可改。
8. **从指定版本修改**（AC-09.4，`domain/work.ts` 的 `reviseFrom`／`cancelRevision`）：从某张结果开始修改时，恢复那一版批准时的风格、布景、比例、生图模型和提示词；商品信息、共创总结和照片是作品本身的事实，保持现在的（之后改过的话，恢复的提示词会被判为过期）。作品上记下 `revision`（从哪张、当时指出的问题、修改前的方案）；批准时把父结果写进批准记录，新一轮的任务和结果都记父结果，界面显示「改自第 N 轮候选 M」；开始生成后 `revision` 清掉。「取消修改」恢复修改前的方案（连着从几张修改时回到最初）。
   - **房间参考**（2026-11-06 发起人选定；**v0.6 取消**，见第 13.5 节）：批准记录里的父结果同时是这一轮的房间参考，生成时商品照片后面带上那张结果图（`client/generation.ts` 的 `sceneRequest`），找不到那张图就如实失败。提示词里各张图的用途由小间写（作品状态写明参考图顺序），代码不往提示词里加字。房间图不进批准快照：`revision` 在开始生成时清掉，放进快照会让这一轮的批准立刻失效、补齐用不了。修改中商品照片已占满模型参考图上限时挡批准，请用户先停用一张（`approvalBlockers`）。方案和批准卡片写「沿用第 N 轮候选 M 的房间和机位」。只管从结果修改的这一轮，之后不再带。
9. **批准前提醒**（2026-11-06 发起人选定，PRD AC-03.4）：`approvalReminders` 列出核心信息里还没接受或忽略的小间建议，显示在批准按钮上方「还缺」的下面，可跳到信息页；不挡批准。小间的作品状态和 `request_approval` 结果里也写明。
10. **写提示词前先处理核心信息建议**（2026-11-06 发起人选定，PRD AC-07.2b）：`promptWriteBlocker`（`domain/approval.ts`）在核心信息还有小间建议没处理时返回原因；`draft_prompt` 据此拒绝，作品状态里写明「现在写会被拒绝」；方案页提示词区显示原因，「让小间写／重写」处理完才能点。只挡小间写，不挡批准（第 9 条）、不挡用户手改提示词和「我核对过，仍然适用」。原因：依据只认已确认的信息，先写后接受，提示词一定被判过期。

## 6. 小间（对话 Agent）

**接口**：`POST /api/chat`

- 请求体：对话消息 + 当前作品状态摘要（由浏览器在每次发送时附带）+ 所选对话模型。
- 服务端：`streamText`，`instructions` 为系统指令（固定规则 + 作品状态摘要），`tools` 为工具定义（只有参数格式，没有执行代码，所以每次请求只走一步），调用前按估价在账本预留，`onEnd` 里按实际 token 结算。
- 商品照片：模型能看图时，每次请求附上当前在用的原图缩略图（长边 768 像素；A 路线再加选定的白底图），最多 6 张；不能看图的模型不发照片，状态摘要里写明。
- 浏览器：`useChat`，在 `onToolCall` 里执行工具并用 `addToolOutput` 交回结果；`sendAutomaticallyWhen` 在工具结果齐了时自动继续，单轮最多自动续 `BUDGET.chat.maxSteps`（8）次，到上限停下并在对话里说明。

**工具清单**（对应 PRD AC-11.2；★ 表示只能「提议」，由用户在卡片上确认；21 个全部已接，每个工具的硬规则有单元测试）：

| 工具 | 作用 | 硬规则 |
| --- | --- | --- |
| `update_info` | 写商品信息 | 只能写成「待确认建议」 |
| `record_story` | 记录用户讲的灵感、主题、情绪 | — |
| `offer_picks` | 「我不知道」时给出 2～4 个方向卡片 | 点卡片只是把选择发回给小间 |
| `draft_summary` | 起草三项共创总结 | 只能是草稿，确认由用户点；生成中拒绝 |
| `set_style` | 改风格卡（色调、背景、光线、摆放、道具、构图、表达） | 生成中拒绝；`basis: 'said'` 必须附用户原话 `quote`，核对不过记为「小间推荐」（AC-05.1a） |
| `apply_scene` | 套用布景模版或已存布景 | 生成中拒绝 |
| `set_ratio` | 改比例 | 会让旧批准失效；生成中拒绝 |

| `resolve_prompt_sync` | 用户手改提示词后报告核对结果 | 有矛盾时列出、不能批准；生成中拒绝 |

| `note_feedback` | 记录用户对候选图的意见（问题标签、原话） | 两项验收由用户点；可同时「从这一张修改」，生成中拒绝 |

**硬规则在哪里保证**：在浏览器的工具执行器里检查，违反时不执行，并把原因作为工具结果返回给模型，让它向用户解释（AC-11.5）。批准、确认总结、同意保存布景或风格，这些操作只存在于界面按钮里，没有对应的工具。

**推荐怎么落地**（开发时对 AC-05.1、硬规则 3 的落实方式，未请发起人逐项确认）：商品信息只能写「待确认建议」、共创总结只能写「草稿」，都要用户点了才生效；风格卡的推荐（`set_style` 的 `basis: 'recommend'`）直接写进风格卡，标「小间推荐」和理由，批准方案时视为确认，用户随时可在画布上改。

**「你说的」要有原话**（2026-11-06 发起人选定，PRD AC-05.1a）：`set_style` 标 `basis: 'said'` 时必须附 `quote`。执行器用 `domain/said.ts` 的 `saidQuoteFound` 核对：去掉空格和标点后，片段（至少 `SAID_QUOTE_MIN` 个字，`config/style.ts`）要出现在用户发过的消息里，或出现在用户手改提示词时新写、小间原文里没有的内容里；核对不过记为「小间推荐」，工具结果写明「是建议、不是用户说的」。用户的消息由对话面板传给执行器（`ExecDeps.userTexts`），因为工具在回复中途执行，这时对话还没存进数据库。只核对片段在不在，不判断和这一项是否相关；卡片在「你说的」下面显示原话，相关不相关交给用户看。

**小间什么时候说话**：只在用户发消息、或点画布上「让小间写／重写／核对／重新整理」「告诉小间哪里不对」时回应。生成完成、确认资产或总结、验收这些画布上的事不会通知小间，它不会自己开口；回访时也不会主动打招呼。这是 AC-11.3、AC-01.2 的缺口；自动开口每次都是一次真实对话调用，要不要做、在哪些节点做，待发起人决定。

**失败处理**：模型调用失败或超时，对话里显示真实错误和「重试」按钮（有次数上限），不用固定话术冒充回复；画布照常可编辑（AC-11.6）。超时：`streamText` 的 `timeout`，首字 75 秒、整轮 150 秒（`config/budget.ts`，本机网络慢时一轮要 14—70 秒，留了余量），超时如实报错、可重试。

**切换模型**（AC-08.7、AC-11.8）：对话框里的输入组件（Prompt Bar）放两个模型选择器，分别选对话模型和生图模型，清单来自 `/api/config`。对话模型默认 `qwen3.8-flash`（能看图、能调用工具），可切换 `deepseek-v4-flash-vision-exp`（`deepseek-v4-flash` 带图会 404，2026-11-01 实测）。现状：已实现（`components/chat/composer.tsx`，用 Prompt Bar）；生成中不能换生图模型；小间只在用户要求时用 `set_image_model`。

**假对话模型**（开发和自动化测试用，`server/fake-chat.ts`）：`FAKE_CHAT=1` 时对话接口不调用模型、不花钱、不记账，按用户最后一句里的「【测试：信息】」「【测试：总结】」等标记照剧本调用工具（剧本见 `FAKE_SCRIPT`，单元测试保证每条都符合工具参数格式）；没有标记时回复写明「测试对话模型，不是 AI」。顶栏标「测试模式」，回复下方标「由 测试对话（不是 AI） 回复」。生产环境即使设了也不生效。

## 7. 生图

**接口**：`POST /api/images` 提交，`GET /api/images/[id]` 查询。

- 网关：AIHubMix 统一生图接口 `/ai/v1/images/generations`，异步模式（账户已开通）。
- 每次生成提交**两个独立任务**（各出 1 张），一张失败不影响另一张，可单独补齐（AC-08.5）。
- 参考图：B 路线用已确认的原图（不超过模型上限）；A 路线用白底图加细节图。从某张结果修改时，再在最后加上那张结果作房间参考（第 5 节第 8 条），总数不超过模型上限。
- 服务端拿到结果后立刻下载，交回浏览器存进 IndexedDB（网关的结果只保留 1 小时，最多下载 3 次）。图片已经生成就已扣费，取回时遇到临时错误（断网、网关 5xx）最多再试 3 次（`config/budget.ts` 的 `GENERATION.downloadTries`），仍失败时如实写「生成好了，但取回或保存图片失败」，由商家决定是否补齐。
- 状态如实显示：排队中、生成中、成功、失败；没有进度百分比就不显示（AC-08.4）。
- 已知限制：等 10 分钟没结果判失败（`GENERATION.timeoutMs`）；网关之后若完成仍会扣费，结果拿不回来。（2026-11-01 核查时列出的另外 4 条——任务恢复只在工作区、两个标签页重复存结果、参考图不重新编码、结果没有缩略图——已在检查点 7 修掉。）
- 模型参数差异（Gemini 用 `aspect_ratio`，GPT、Qwen 用 `size`，Seedream 默认出 2048 像素等）集中写在 `config/models.ts`。
- 白底图比较两种做法（PRD 4.3）：①生图模型加白底提示词，走同一个接口；②保留原像素的抠图，发起人曾选定阿里云「商品分割」，后指示先不接。见本节「白底图的两种做法」。
- **假生图网关**（开发和自动化测试用，`server/fake-images.tsx`）：`FAKE_GATEWAY=1 npm run dev` 时三个生图接口不调用模型、不花钱、不记账，几秒后返回写着「TEST IMAGE · NOT AI GENERATED」的测试图，`/api/config` 返回 `fake: true`，顶栏标「测试网关 · 图片非 AI 生成」（AC-08.6）。提示词里带「【测试：失败一张】」时同一段提示词第一次提交的那张失败，带「【测试：全部失败】」时每张都失败，用来测部分失败、补齐和次数上限。生产环境（`NODE_ENV=production`）即使设了也不生效。任务存在 `globalThis` 上，热更新和各接口各自加载模块时也共用。

### 白底图的两种做法（PRD 4.3、AC-02.2、AC-02.3）

A 路线（先白底再生成）需要白底图。两种做法都做，结果都存成派生素材（`assets.origin = 'white'`，`method` 记做法，`parentId` 记原图）；商家对照原图选用一张（`work.whiteChoice`），再确认资产。原图永远不动。

**① 实际做法**（2026-11-01 检查点 5 已实现）：

- `config/white.ts`：固定白底提示词（完整入框、不改结构、纯白背景、不加文字，带上「不能改的细节」）、比例 1:1、每张原图最多做 3 次（含失败）。
- `domain/white.ts`：`whiteCheck`（只在 A 路线、只给在用的整体或背面原图做；生成中、同一张正在做、次数到上限时拒绝）、`whitesOf`、`makingWhite`；有单元测试。原图停用后，从它做出的白底图不再进参考图（`referencesOf`）。
- `client/generation.ts` 的 `makeWhiteByGeneration`：建 `kind: 'white'` 的任务，和场景图共用提交、轮询、取回重试；完成后存成 `method: 'generate'` 的白底图（记 `parentId`），任务记 `whiteAssetId`。花费照常累加进作品。白底任务不算「生成中」，不锁方案；但做白底时不能删作品。

## 12. 凭据统一管理与协作者转发（v0.5，2026-11-01 已确认并实现）

依据：发起人 2026-11-01 选定的《服务端与 API 密钥统一管理方案》（发起人本机文件，不在仓库）和同日的两项选择（agents.md「API 密钥与调用权限」）。后台一侧见 `管理后台/prd/PRD.md` v1.1 和 `管理后台/prd/技术方案.md`。本节写主产品这边的做法；代码已实现（2026-11-01），验证见 `管理后台/prd/验收记录.md`「v1.1」。部署未做。

### 12.1 已定的做法

- AIHubMix key 在管理后台录入，加密后存进服务器上的凭据文件；主产品只读这个文件，自己不提供任何写 key 的接口。
- 一套 key 所有人共用：商家通过网站用；协作者本地开发时，把发往 AIHubMix 的请求转给服务器（12.5），真 key 不离开服务器。
- 后台和主产品放在同一台香港服务器上，后台只监听服务器本机，发起人经 SSH 隧道打开。
- 真实用户的护栏（身份、个人额度、频率）由发起人以后安排，本节不做（限制见 12.8）。

### 12.2 凭据来源

`CREDENTIAL_SOURCE` 在启动时读取，改了要重启；三种来源互不回退。

| 取值 | 用在哪 | 怎么取 key |
| --- | --- | --- |
| `env`（不设时的默认值） | 现在的本地开发 | `.env.local` 的 `AIHUBMIX_API_KEY`，和现在一样 |
| `file` | 香港服务器 | 读 `CREDENTIALS_PATH` 指向的凭据文件，用 `CREDENTIALS_MASTER_KEY` 解密 |
| `relay` | 协作者本地 | 不拿真 key：请求发到 `MODEL_RELAY_URL`（只填服务器地址，路径由代码按供应商拼上），带团队口令 `MODEL_RELAY_TOKEN` |

- `file` 模式下文件缺失、损坏、解密失败或已停用时，给出可读原因并拒绝调用，不改用环境变量。
- 每次调用都重新读凭据文件（文件很小），后台一改，下一个请求就用新的，不用重启。对话和生图现在本来就是每次请求现取 key（AI SDK 的 `apiKey` 传的是函数），只要换掉取 key 的函数。
- 改动点：`src/server/env.ts` 的 `apiKey()` 换成新文件 `src/server/credentials.ts`（server-only）里的统一读取；`/api/config` 的「是否已配置」改用同一来源（12.4）。

### 12.3 凭据文件

- 格式和加解密写在 `src/server/credential-file.ts`。它只依赖 `node:crypto`、只用可擦除的 TS 写法，也不引 `server-only`：管理后台要用 Node 直接加载它（和后台现在读 `models.ts` 的方式一样），这样两边只有一份实现。浏览器代码引用它会在打包时报错。
- 算法：AES-256-GCM，每次加密重新生成 12 字节随机 IV；附加数据绑定格式版本和供应商（`yijian-credential:v1:aihubmix`）。主密钥是 32 字节随机数的 base64，长度不对直接报错。
- 内容：`schemaVersion`、`revision`、`updatedAt`；`providers.aihubmix` 存状态（`active`／`disabled`），当前 key 的密文、尾号和保存时间，以及替换时留下的上一把 key（`previous`：密文、尾号、替换时间）；`relay` 存团队口令的 SHA-256 散列、尾号和状态；另有操作记录（时间、动作、尾号）。文件里没有任何明文。
- 只有管理后台写这个文件（原子替换加 revision 校验，见后台技术方案），主产品只读。文件放在仓库之外，比如 `/var/lib/yijian/credentials.json`，目录权限 700、文件 600。

### 12.4 读取规则

- **新请求**（对话、提交生图）：状态必须是 `active`，用当前 key。
- **已提交的生图**（查状态、取图）：AIHubMix 文档写明「任务及内容按创建任务时的 Bearer Token 隔离」，换 key 后，旧任务很可能只有旧 key 才取得到。所以：
  - 停用只拦新请求，不拦查询和取图，免得已经扣费的图拿不回来；
  - 当前 key 查旧任务返回 404（`task_not_found`）时，如果上一把 key 替换还不到 24 小时，改用它再查一次。24 小时写在 `config/credentials.ts`。
- 从 `env` 切到 `file` 时如果换了 key，切换前提交的任务同样可能取不回，所以切换要选在没人生图的时候。
- `/api/config` 返回 `credential: { source, ready, revision, reason }`，不含尾号和密钥；原有的 `configured` 保留，值等于 `ready`。后台用 `revision` 核对主产品读到的是不是同一份文件。

### 12.5 协作者转发

**服务器一侧**：新接口 `/api/relay/aihubmix/[...path]`。只在 `file` 模式、而且后台生成过团队口令时开放，否则返回 404。

- 校验 `Authorization: Bearer <团队口令>`：算散列后用定长比较。
- 只放行 4 个转发路径：`POST v1/chat/completions`、`POST ai/v1/images/generations`、`GET ai/v1/images/{id}`、`GET ai/v1/images/{id}/content/{result_id}`，编号按格式校验；另加 `GET status`，告诉协作者本地服务器这边能不能用。其余路径一律 404。上游只发往 `GATEWAY` 里的固定域名。
- 模型必须在服务器的 `config/models.ts` 里，规则同 `/api/chat`、`/api/images`。沿用 `budget.ts` 的单张估价上限和总预算，记进服务器账本，条目加 `via: 'relay'`。对话按请求字数和输出上限预留估价，流结束时按返回的用量结算，拿不到用量就按估价记（宁多勿少，同现有规则）。
- 流式回复原样转回；上游的错误文字先脱敏（12.6）再返回。不记录请求内容，里面有照片和对话。

**协作者本地**（`relay` 模式）：

- `aihubmix.ts` 的两个网关地址换成服务器地址（`MODEL_RELAY_URL`）加 `/api/relay/aihubmix` 下对应的路径，凭据换成团队口令；`MODEL_RELAY_URL` 带了路径会直接报错，不拼成两层；结果下载地址 `content_url` 是网关域名，换成转发地址后再取。
- 小间的系统规则、工具、模型选择都在协作者本地执行，所以协作者改的代码能用真实模型测到；只有发往 AIHubMix 的那一步经过服务器。
- `/api/config` 在 `relay` 模式下请求服务器的 `status`（短超时），如实显示服务器那边能不能用。
- `/api/images` 收到服务器回的 `not_configured`（服务器的 key 没配好或已停用）时退回本地预留：请求没有发到 AIHubMix（联调时发现后补上）。

### 12.6 脱敏

错误文字返回浏览器或写进日志之前，先把当前 key、上一把 key、团队口令的原文换成「尾号 xxxx」，再把 `sk-` 开头的长串整体替换掉。

### 12.7 部署要点（补充交接文档第 10 节）

- 主产品和后台用同一个系统用户运行，共用一份环境变量文件（权限 600），写 `CREDENTIAL_SOURCE=file`、`CREDENTIALS_PATH`、`CREDENTIALS_MASTER_KEY`；服务器上不再放 `AIHUBMIX_API_KEY`。服务器第一次部署就用 `file` 模式（服务器上没有旧的环境变量要迁移）。发起人定（2026-11-01）：正式上线前本地开发照旧用 `env`；上线后本地开发一律走 `relay`，用后台管理的那套 key。
- 主产品 `next start` 只监听 127.0.0.1，经 HTTPS 反向代理对外；后台不经反向代理。反向代理的请求体上限要放大（nginx 默认只收 1MB），至少容纳 4 张 2048px 参考图的 base64（v0.6 每次最多 4 张：合成用背景图＋三视图，`/api/images` 按 `MAX_REFS` 和所选模型的 `maxRefs` 限制；尺寸见 `config/upload.ts`），具体值部署时实测。现有的 `/api/images` 也需要这一条。
- 主密钥单独备份（比如放密码管理器），不和凭据文件放在一起。主密钥丢了也能恢复：在 AIHubMix 重新生成 key，到后台重新录入。
- 服务器地址和团队口令都不进公开仓库，私下发给协作者，写进各自的 `.env.local`。

### 12.8 已知限制（发起人已知悉的取舍）

- 真实用户的护栏做好之前，网站自己的 `/api/chat`、`/api/images` 对知道网址的人仍是开放的；团队口令只管转发入口。兜底靠 AIHubMix key 的额度和服务器账本的总预算。
- 一套 key、一个团队口令：AIHubMix 和账本只分得出「网站」和「转发」，分不出是哪位协作者花的。某位协作者退出时只能换口令，其他人也要跟着换新的。
- 换团队口令后，协作者进行中的生图会取不回。
- 后台没有账号，SSH 就是门槛；操作记录里不区分是谁。

### 12.11 以后增加供应商

发起人 2026-11-01：供应商（发 key 的平台）目前只有 AIHubMix，以后可能加别的平台，可能是模型出品方的官方接口，也可能是别的中转。现在不做，记下要改的地方。

- 已经按供应商分开的：凭据文件按供应商存（`providers.<供应商>`，加密附加数据也绑定供应商）；转发路径带供应商（`/api/relay/aihubmix/…`）；后台凭据表每行显示模型所属的供应商。
- 模型配置：每个模型要写明走哪个供应商、在该供应商那里的 API ID 和价格。同一个模型走不同供应商时名字和价格可能不同，算两条。
- 网关：对话大多是 OpenAI 兼容接口，换地址和 key 就行；生图各家协议不同（AIHubMix 用的是它自己的异步任务接口），每家要单独写一套，这是加供应商的主要工作量。
- 凭据：`credential-file.ts` 的 `PROVIDER_IDS` 加一项。像阿里云这样要两项凭据（AccessKey ID 和 Secret）的，凭据文件要升一版格式，后台表单也要两个输入框。
- 状态：`/api/config` 和后台的「主产品当前读取」改成按供应商分别报；转发按供应商分路径，各自一份模型白名单。
- 协作者的 `MODEL_RELAY_URL`：已改为只填服务器地址（发起人 2026-11-01 定），代码按供应商拼 `/api/relay/<供应商>`，加供应商时协作者不用改配置。

### 13.2 流程、步骤与作品状态

- `Work.flow: 'home' | 'template'`，建作品时按入口定；流程二改为自己生成背景时改成 `home`。
- 步骤用编号而不是序号：`'product' | 'info' | 'backdrop' | 'placement' | 'result'`。`config/steps.ts` 按 `flow` 给出两套顺序和名称。所有用步骤的地方改成按编号：`Blocker.step`、`stepStates`、`currentStep`（`domain/status.ts`）、画布切换、`show_step` 工具参数、画布跟随规则（第 8 节）。
- 作品状态推导（`domain/status.ts`）按 PRD 5.3 新增：信息待处理、背景待选择方式、共创中、总结待确认、背景待批准、背景生成中、背景待选定；流程二和「用模板库里的」没有共创和背景生成的状态。每一步的「完成」条件：商品＝三个角度都有已确认的三视图；信息＝沿用现有 `infoDone`（`domain/info.ts`）：必填项已填或标了未知，且核心信息没有未处理的建议；背景＝已选定背景图（新生成时还要总结已确认）；摆放＝合成批准有效；出图＝有两项都满意的结果。

### 13.3 商品：照片与三视图

- `config/upload.ts` 的 `ASSET_KINDS` 改为 `front` 正面、`side` 侧面、`back` 背面、`detail` 细节。商品画布固定三个角度的上传位加细节照区；首页和对话里上传的照片先进「未分类」，用户在商品画布里选类型（小间可以建议，不能代选）。缺正面、侧面、背面任何一张在用的照片时，「生成三视图」不能点并写明缺哪张。
- 三视图：每个角度一个独立任务（`tasks.kind = 'view'`，记 `view` 角度和来源照片），参考图为该角度原图＋正面原图（正面那张只带一次）；固定提示词写在 `config/views.ts`，写明每张参考图的用途（第 1 张是要生成的角度，第 2 张是整体参考）、纯白背景、只保留照片里看得到的结构、不改颜色数量和连接、完整入框、无文字，带上「不能改的细节」。比例 1:1，每个角度最多 3 次（含失败）。
- 结果存为派生素材（`assets.origin = 'view'`，`view` 角度，`parentId` 原图，`confirmed`）。对照弹窗按角度并排放大，逐张「可以用」。换掉或停用某个角度的原图：该角度的三视图作废，已有合成批准失效。
- 三视图不需要批准，只能由用户点按钮；小间用 `propose_views` 放提议卡片。生成三视图时锁住照片（不能换、停用）。

### 13.4 背景

- 背景画布顶部二选一：「用模板库里的」（列出内置和已沉淀、未删除的背景图）和「自己生成」。
- 自己生成：背景共创（沿用 `record_story`、`offer_picks`、`draft_summary`，总结由用户确认）→ 背景风格卡（色调、背景、光线、装饰道具、背景禁止项）→ 小间写背景提示词（`draft_backdrop_prompt`）→ 背景批准 → 2 个背景任务（`tasks.kind = 'backdrop'`）→ 用户选 1 张（界面写「图里不能有饰品」）→ 可选「沉淀进模板库」（起名字）。
- 背景提示词的系统指令：画面里没有任何饰品、首饰和文字；写清光线方向和软硬；按品类和尺寸留出主体位置和台面。比例固定 3:4（`config/backdrops.ts`）。
- **背景批准快照**（单独的类型 `BackdropSnapshot`）：背景风格五项、共创总结、核心信息里的品类和尺寸、生图模型、背景提示词、张数 2；比例固定，不进快照。依据指纹同这几项（去掉提示词和张数）。PRD AC-07.3 同步改。
- 必填：生成新背景时色调、背景、光线必填（`BACKDROP_REQUIRED`）；用模板时不检查背景风格（内置模板参数为空）。
- 改了共创总结或背景风格：已选定的背景图不作废，背景画布提示「背景是按旧的内容生成的」；背景提示词照常过期。
- 选定背景后，背景五项以背景图记录的参数为准、只读；内置模板参数为空时画布显示「示意模板，无参数」。
- **背景做法跟着背景图的来源走**（2026-11-23 修代码评审第 1、2、5、6、10 条时写定）：选的是这件作品自己生成的背景图（`!builtin && workId === 这件作品`，沉淀没沉淀、删没删都算）→「自己生成」，共创和总结都属于这张图；内置模板和别的作品沉淀的 →「用模板库里的」。规则在 `domain/backdrops.ts` 的 `backdropModeOf`，入口只有一个：`domain/work.ts` 的 `chooseBackdrop`，画布上点「用这张」、在模板库里点一张、小间的 `use_backdrop`、「从这一版修改」都用它。所以在「用模板库里的」下点这件作品自己沉淀的那张，会切到「自己生成」，「用模板库里的＋自家背景」不再出现。自家背景只出在流程一，`chooseBackdrop` 定为「自己生成」时把流程兜底设成流程一；`setBackdropMode` 里「自己生成 ⇒ 流程一」不变。
- 这件作品自己的背景图，沉淀后又从模板库删除，本作品照常能重选（删除只挡别的作品套用）。合成或背景生成中都不能换背景（画布按钮、`pickBackdrop`、`use_backdrop` 同一条件）。
- 模板库列表只有一个顺序（`domain/backdrops.ts` 的 `libraryList`）：沉淀的在前、新沉淀的在前，内置在后；画布「用模板库里的」、首页、给小间的作品状态都用它。

### 13.5 摆放与合成

- 摆放卡：摆放（含展示用具：支架、挂钩、首饰托盘）、构图、合成禁止项，加比例（全流程唯一可选的比例，`set_ratio` 只改它）和生图模型。必填：摆放、构图（`SCENE_REQUIRED`，取代现在的 `STYLE_REQUIRED`）。
- 小间写合成提示词（沿用 `draft_prompt`）：没有已选定的背景图或三视图没确认时拒绝；系统指令要求写明参考图顺序和用途（第 1 张背景：保持取景、材质、光线；第 2—4 张三视图：商品只以三视图为准）、按尺寸写饰品大小、阴影和反光跟背景光线一致、背景里没有展示用具时按摆放加上、可按所选比例重新构图；背景没有参数时按小间看到的背景图描述。代码不往提示词里加字。
- **合成批准快照**（现有 `Snapshot` 改造）：`references`（3 张三视图编号）、核心信息、共创总结（没做共创时为空）、`backdropId`、摆放、构图、合成禁止项、比例、生图模型、合成提示词、张数 2；去掉 `sceneId`、`route` 和背景五项。`domain/snapshot.ts` 的 `BASIS_PARTS` 加「背景图」，两版对比随之显示（AC-09.5）。
- 生成：参考图 = 背景图＋3 张三视图（`sceneRequest` 改写，不再带父结果图）。`approvalBlockers` 按批准种类拆开，删掉房间参考的上限检查；4 个候选模型上限都是 4，以后换上限更小的模型时挡批准。

### 13.6 数据模型（Dexie 升到第 2 版）

### 13.12 让小间跟上画布（PRD AC-11.3a—c）

**现状**：用户每发一条消息，浏览器都把作品状态摘要（`agent/state.ts`）附给小间，里面已有待确认的信息建议、草稿总结、手改未核对的提示词。画布输入框只在打字时有本地草稿（`components/ui/draft-field.tsx`），失焦就保存。缺的是：画布操作不会叫起小间；v0.6 的状态没进摘要；小间不知道最近改了什么。

**1. 系统消息**：交接、生成通知、验收通知都是浏览器以用户身份发出的消息，但消息上带标记（`metadata.system = 'handoff' | 'notice'`），界面显示为小卡片，不当成用户原话：

- 「你说的」原话核对（`userTextsRef`，`components/chat/chat-panel.tsx`）排除带标记的消息；`saidQuoteFound` 的手改提示词核对同时覆盖背景提示词和合成提示词。
- 内容由代码按数据生成，不经模型。

**2. 「下一步」交接（AC-11.3a）**

- 商品、信息、背景、摆放四步画布底部放「下一步」；前置条件没满足时不可点并写明缺什么。点了：先让聚焦的输入框失焦保存 → 画布切到下一步 → 发交接消息。
- 内容：商品＝用了哪几张原图、三视图各角度已确认；信息＝核心信息四项（已确认的值、未知项）、选填项、还没处理的建议；背景＝用模板还是自己生成、共创三项总结、背景风格五项、选定的背景图、是否沉淀；摆放＝摆放、构图、禁止项、比例、提示词和批准状态。
- 出图步骤没有「下一步」：用户把一张候选的还原度和风格都点完时，发验收通知（哪一张、两项结果、问题标签和说明）。
- 系统指令要求小间收到交接或通知后按固定结构回话：**我理解的现状** → **还没确认或有矛盾的地方** → **下一步**。

**3. 已改未确认的内容（AC-11.3b）**

- 作品状态摘要补上：流程和当前步骤；三视图各角度（未生成／生成中／待确认／已确认）；背景选择方式、背景候选（待选定）和选定的背景图（名称、参数或「示意模板，无参数」）；两段提示词各自的状态；两种批准是否有效；模板库里可选的背景图（名称和参数）。每项标「已确认」或「已改、未确认」。
- `Work.lastHandoff`：上次交接时的文字快照。摘要加一段「自上次交接以来用户改了」，逐项列改前改后（复用 `diffSnapshot` 的做法）。
- 用户让小间改时，小间用现有工具改；硬规则不变。用户正在输入的框不会被覆盖（`DraftField` 已保证）。

**4. 生成通知（AC-11.3c）**

- 时机：三视图一批（3 个角度都有结果）完成、单张重做完成、背景 2 张都有结果、候选 2 张都有结果（含部分失败）。附结果缩略图（13.9 的附图规则）。系统指令写明小间可以指出明显问题，但不能替用户判定满意。
- **持久化与排队**：任务结束时在任务上留 `notifiedAt = null`；对话面板打开且空闲（`status === 'ready'`，且不在 `sendAutomaticallyWhen` 自动续步之间）时，把还没通知的任务按批合并成一条消息发出，并写上 `notifiedAt`。刷新后由 `resumeActiveTasks` 收回的结果，面板打开时补发。按任务编号去重，两个标签页同时开时只发一次（写 `notifiedAt` 用事务，先写先得）。
- 「空闲」的判断和自动续步用同一个条件：`status === 'ready'` 且 `lastAssistantMessageIsCompleteWithToolCalls` 为假（`components/chat/chat-panel.tsx` 的 `sendAutomaticallyWhen`），避免插进工具结果和自动续步之间。上一轮出错或撞上单轮 8 步上限时，队列不自动发，等用户重试或发新消息后再发。
- 小间正在回话时点「下一步」：画布照常切换，交接进同一个队列；队列里只记「哪一步交接了」，**内容在发出那一刻按当时的作品数据生成**，不发过时的内容。
- 单轮最多 8 步（`BUDGET.chat.maxSteps`）照旧；系统消息各自算新的一轮。
- **发送队列**（2026-11-23 修代码评审第 4、12 条，`client/agent-queue.ts`）：
  - 对话面板每次数据变化，先用现成的作品数据判断有没有要发的（`queueDue`：排队的交接、可以发的生成通知、停手够久的验收通知；验收还要等就到点再看），有才去读库认领。
  - 认领和发出由 `sendQueued` 管：同一件作品同一时间只跑一个（认领要写库，写库又会让面板再来取）；取到后在同一步里看对话还空不空闲，空闲才发。不空闲（用户开始打字、刚发了消息、面板卸载了）就先留着，下次空闲时先发它，留着的时候不再认领新的。跑的过程中又有人来取过，跑完再看一次。
  - 空闲状态在提交时（布局副作用）记下，卸载时记为不空闲。AI SDK 7 的 `sendMessage` 不防并发，这几条就是为了不让两条请求同时跑。
- 附图带编号（`ChatPhoto.id`）：生成通知里排在最前的结果图，不会再按一般对话的顺序加第二遍（评审第 3 条）。
- 作品状态里的模板库只列最近沉淀的 10 张（`BUDGET.chat.libraryInState`）加全部内置模板，其余写「另有 N 张」；`use_backdrop` 照样认没列出的编号。作品状态的上限 2 万字（`BUDGET.chat.stateMaxChars`，`/api/chat` 按它校验）；沉淀 100 张参数写满的背景、两段提示词写满时实测约 1.1 万字（评审第 9 条）。

**5. 花费与测试**

- 一件作品约 4 次交接、3—5 次生成通知、1—2 次验收通知（共约 8—11 次），Qwen 3.8 Flash 估价每次约 0.001—0.003 美元（附图时更多），计入账本和作品花费，受对话预算上限约束。

### 14.4 问过再代点（B 类）

例子（三视图）：

> **小间**：三张三视图都出来了。正面和背面跟原图对得上；侧面那张扣头的角度我看不准，你对照一下原图。要我替你把三张都点「可以用」吗？
> 〔卡片「要我替你点吗？」：正面三视图可以用；侧面三视图可以用；背面三视图可以用。［同意］［不用了］〕
> **用户**：正面和背面可以，侧面我再看看
> **小间**：正面、背面替你点了「可以用」，侧面等你看完再说。〔卡片变成「替你点了 2 样（你说「正面和背面可以」）」〕

- **小间问**（`ask_confirm`）：列出要替用户点的几样，每样是一个固定动作：确认某个角度的三视图、接受某项信息建议、把某项标「未知」、确认共创总结、选定第几轮背景几、把选定的背景图沉淀进模板库（带名字）、给第几轮候选几填两项验收、流程二改自己生成背景。代码先查每样现在能不能点（和画布按钮同一条件），不能点的拒绝并说明。能点就在作品上记一条请求：编号（这次工具调用的编号）、这几样动作、每样东西当时的样子（三视图编号、建议的值、总结原文、背景图编号、验收的现值、流程）、时间，状态「等回复」。同一时间只有一条在等，再问一条，旧的作废。
- **卡片**：列出这几样和「同意」「不用了」两个按钮。按钮等于替用户在输入框里打这两个字发出去，不直接执行，代点只有下面一条路。三视图那几样带「对照」，打开商品里的对照弹窗；背景候选和沉淀写一句「图里不能有饰品」。
- **小间代点**（`confirm_for_user`）：参数是用户表示同意的原话（逐字照抄）；用户只同意一部分时，写明点哪几样。代码核对三条，都对上才执行：
  1. 有一条请求在等回复；
  2. 请求之后用户发过消息（浏览器代发的交接和通知不算），原话能在这些消息里逐字找到；
  3. 要点的每样东西和问的时候一样；用户这期间自己点过、改过，或者又生成了新的，整条请求作废，请小间重新问。

  每样调用和画布按钮同一个函数；做完请求记为「已代点」，卡片写明替用户点了哪几样、引用的原话。
- 代码不判断那句话是不是同意的意思，由小间理解（和 AC-05.1a 核对「你说的」一样）；只要求原话要是用户某一小句（以标点或空格分开）或连着几小句的全文，所以「不同意」里的「同意」、「不太好」里的「好」不算，「没问题」整句可以（2026-11-23 代码评审后定，见 14.13）。这挡不住小间理解错，所以卡片上写明它引用的原话，用户看得到。点错的多数能改回来：验收可以重新点，信息可以在画布上改，背景可以重选，沉淀的可以从模板库删除，总结让小间重新起草就回到草稿（用户在画布上改字不改确认状态）。三视图「可以用」点错了，在对照弹窗里点「取消确认」（14.11 第 4 条）。改不回来的只有流程二改流程一（之后再选模板也还是流程一，只是步骤顺序不同）。
- 用户自己先说了「帮我把三视图确认了」，小间也先放卡片问一次：发起人说的是「问我是否同意、我回复同意就代点」。这样多一轮对话，但每次代点之前用户都看过要点什么。
- 代点的验收不再发验收通知（小间自己点的，知道结果）。试用事件记 `by: 'agent'`；试用记录 CSV 加一列「小间代点」次数，分得出验收是谁点的（验收结果进试用记录）。

### 14.5 弹确认框（C 类）

- `request_delete` 的目标：照片（停用）、模板库里的背景图、这件作品。`set_photo_kind` 会顶掉或移走某个角度现在的照片时，也先弹确认框。
- 工具执行时，页面弹出和画布上同一个确认框，标题前加「小间想」（如「小间想从模板库删除「雨后清晨」？」），正文一样；工具等用户点完才返回。点「确认」就执行；点「取消」或按 Esc，返回「用户取消了」，小间不再追问，除非用户又说要删。
- 等用户点确认框时，对话不算空闲，交接和通知先不发。写代码时查了 AI SDK 7：`onToolCall` 在处理回复流的同一个任务里被等待，工具执行（含等确认框）期间状态一直是「回复中」，本来就不会被当成空闲（写法初稿说「会被当成空闲」不对，已更正）。仍在空闲条件里加一条「最后一条回复里有工具调用没结果就不算空闲」兜底（`pendingToolCall`）。
- 对话只在一轮结束或出错时保存，确认框开着时关掉页面，这一轮本来就不会存下；只有中途被停下等少见情况会存下没结果的调用。服务端转换消息时默认不丢弃没结果的调用（`convertToModelMessages` 的 `ignoreIncompleteToolCalls` 默认关），下一次对话会出错，所以读出对话时给它补一条结果「这次调用没有结果（页面关掉或中途停下了），可能没执行」（`closeDanglingCalls`）；参数还没收全的调用直接去掉。
- 删除这件作品：确认后删掉并回到作品页，对话跟着删掉，不再返回结果。

### 14.6 生成只能用户点（D 类）

- 去掉 `start_backdrop_generation`、`start_generation`：批准和发起生成是同一下（滑动「批准并生成」），这两个工具只在「批准了却没发起」时有用；那时用户再滑一次即可，记成新的一版批准。
- `retry_candidate` 改成 `propose_retry`：放一张「补齐这一张」卡片（和 `propose_views` 一样），用户点了才补；放卡片和点按钮时都查 `retryCheck`，不能补就写明原因。
- `propose_views`、`request_approval`、`offer_export` 不变。
- 批准仍只由用户做：在这个产品里批准就是发起生成的那一下，按「生成只能用户点」处理（14.11 第 2 条，不拆）。批准了却没发起时，对话里的批准卡片照样放出滑块，再滑一次就是新的一版。

### 14.7 小间推进下一步，画布跟着走

- `next_step`（参数：做完的那一步）：条件和「下一步」按钮一样（`handoffBlocker`），没做完就拒绝并说缺什么；做完就让画布切到下一步，记下交接快照（`lastHandoff`，「自上次交接以来」从这里重新算），去掉这一步还在排队的交接。
- 不发交接消息（小间自己推进的，用不着再告诉它）。工具结果里带上这一页的内容（和交接消息同一段文字，`handoffText`），小间据此用一两句话说这一步定了什么、接下来做什么。
- 系统指令：一步做完、用户没在接着改这一步时，先说明这一步定了什么，再用 `next_step` 推进。出图是最后一步，没有 `next_step`。

| 情况 | 画布 |
| --- | --- |
| 用户点「下一步」 | 切到下一步，发交接，小间回话（不变） |
| 小间 `next_step` | 切到下一步，不发交接（新） |
| 小间 `show_step` | 切到那一步（不变） |

### 14.11 发起人拍板的（2026-11-23：都按代理建议，1A 2A 3A 4A）

1. **哪些算「要你确认的事」**（定：归 B，先问）：按发起人说的「所有涉及到要我确认的」，接受信息建议、选定背景候选、沉淀进模板库都归 B（先问），和代理之前在 `agents.md` 记的「小间直接做」不一样。理由：信息建议多是小间看照片推测的，直接接受就是把推测当成商品事实写进生图依据；选背景和沉淀要用户看「图里有没有饰品」（AC-06.2）。
2. **批准**（定：不拆）：这个产品里批准就是发起生成的那一下（滑动「批准并生成」），照「生成只能用户点」，批准也由用户滑。另一种是拆开：小间问过后代为批准，再由用户点「生成」，用户多一步操作。建议不拆。
3. **下载**（定：由用户点）：发起人的规则里只有生成要用户点。建议下载也由用户点：往用户电脑里存文件，下载卡片上有「发布时请声明 AI 生成」的提醒（AC-10.5），试用记录也按导出算。代理之前在 `agents.md` 写的「浏览器要求」不准确：网页自己发起下载一般也能下，只是连续下载时浏览器会弹询问。
4. **三视图的「取消确认」**（定：加）：现在点了「可以用」就撤不回，只能花钱重做；小间代点有理解错的可能。建议在对照弹窗里加「取消确认」，改动很小。

代理自定（发起人没改，照此实现；可再调）：改作品名直接改、去掉顶栏的名字建议；用户先开口要求的确认也先放卡片问一次；照片会顶掉或移走某个角度现在那张时弹确认框；卡片按钮等于发文字；小间自己推进时不发交接。

**实现时自主决定、可再调的做法**：

- `ask_confirm` 的每一样参数摊平写（按 `type` 填对应几项），不用嵌套的多选一格式：不同模型对 `anyOf` 支持不一。缺参数时拒绝并写明要填什么。
- 有一样点不了，整张卡片不放，逐条写原因，小间改了再问。东西没变、只是正在生成暂时锁定时，代点先不执行，请求留着。
- 只同意一部分时，只比对要点的那几样有没有变。同一条请求里可以先「选定背景候选」再「沉淀」；只同意沉淀、没同意选定，就要先选定，一样都没点成，请求留着。
- 同意的原话不管标点、空格和大小写，一个字（「好」）也行，但要是用户某一小句（以标点或空格分开）或连着几小句的全文：「不同意」里的「同意」不算（第二轮代码评审后定，见下面）。
- 卡片的「同意」「不用了」只在卡片是最后一条消息时显示；用户回过话后卡片写「还没代点」，用户直接打字同意照样能代点。用户回「不用了」时请求不改状态，小间不代点即可。
- 只能选最新一轮的背景候选（和画布一样，画布只显示最新一轮）。
- 代点的每一样记一条 `proxy` 试用事件；选背景、沉淀、验收、改做法另在原来的事件上记 `by: 'agent'`。试用记录 CSV 加「小间代点」一列，按种类写次数。
- 代点的验收顺手写上 `notifiedVerdict`，不再发验收通知；用户之后再改问题标签或说明，照常通知。
- 小间直接做的改做法、选模板、`use_backdrop` 也记 `by: 'agent'`，但不算代点。
- 小间发起删除作品并经用户确认后，回作品页；这一轮的对话花费记不进作品了（服务端账本照常记）。
- 确认框开着时又来一个（不该发生），前一个按「取消」了结，免得工具一直等。
- `next_step` 的对话记录只写「推进到「X」」，整页内容只给小间看。
