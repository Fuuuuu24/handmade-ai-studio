## 2. 总体结构

```text
浏览器（界面＋本地数据）                          服务端（Next.js 接口，只做代理）            AIHubMix
┌───────────────────────────────┐   POST /api/chat     ┌──────────────────────────┐   对话模型
│ 页面：首页／作品／工作区／风格／布景／历史 │ ───────────────────▶ │ 小间：streamText＋工具定义  │ ─────────▶
│ 工作区：左对话（useChat）右画布      │ ◀─── 流式回复＋工具调用 │ 记账：按 token 计费        │
│ 工具执行器：小间的工具在浏览器里执行   │                      └──────────────────────────┘
│ 规则层：批准、快照、状态机（纯函数）   │   POST /api/images   ┌──────────────────────────┐   生图模型
│ 存储：IndexedDB（作品、图片、对话）    │ ───────────────────▶ │ 提交任务、查询、下载        │ ─────────▶
└───────────────────────────────┘ ◀─── 任务状态／图片   │ 预算与重试上限检查          │
                                                     └──────────────────────────┘
```

- **数据都在浏览器**（PRD O5）。服务端不存作品和照片，只转发请求，并记一本花费账。
- **密钥只在服务端**：现在是 `正式代码/.env.local` 里的 `AIHUBMIX_API_KEY`，不进版本库，也不发给浏览器。v0.5：服务器上改由管理后台录入、加密存文件，协作者经服务器转发（第 12 节，已实现，未部署）。
- **小间的工具在浏览器执行**：模型决定调用哪个工具，工具的执行代码在浏览器里运行并修改本地数据。这样服务端不需要保存作品状态。
- **不设访问限制**（2026-10-31 发起人决定）：试用网址不加邀请码或密码，发起人判断不会有外人使用；花费由服务端的预算上限兜底。
- **硬规则的保证范围**：批准与生成前的检查在浏览器的规则层和工具执行器里做，能挡住模型绕过规则；服务端不存作品，无法校验批准，只负责预算和重试上限。改浏览器代码的人挡不住，试用期可接受。
- **花费按作品记录**：服务端每次调用算出花费，随响应返回；浏览器记在对应的生成任务和对话上，试用记录据此统计每人累计成本（PRD 6.2 记录模板）。做法：生图花费记在任务上并累加进 `work.costUSD`；对话请求开始时元数据 `costUSD` 置 0、结束时写本次花费，浏览器在 `useChat` 的 `onFinish` 里（排除中止和出错）加进作品。中止或出错的对话不累加，服务端账本仍按估价记全，总预算不受影响。

## 4. 数据模型（IndexedDB）

| 表 | 内容 | 关键字段 |
| --- | --- | --- |
| `works` | 作品 | 名称、创建／更新时间、商品信息、共创、风格卡、比例、所选生图模型与对话模型、资产路线 A/B、选用的白底图、提示词、最近一次批准、累计花费、正在从哪张结果修改（`revision`） |
| `assets` | 商品照片与派生图 | 所属作品、类型（整体／背面／细节）、来源（上传／白底，白底图记父图和做法 `generate`／`matting`）、是否停用、被哪张替换 |
| `blobs` | 图片二进制 | 原图、缩略图、白底图、生成图都存这里，其他表只存编号 |
| `messages` | 对话 | 所属作品、AI SDK 的 UI 消息原样保存（含工具调用记录，满足 AC-11.4） |
| `approvals` | 批准记录 | 所属作品、第几版、快照（参考图、路线、核心信息、总结、风格、布景、比例、生图模型、提示词、张数）、用于第几轮、父结果 |
| `tasks` | 生成任务 | 所属作品、类型（场景图／白底图）、所用批准、第几轮第几张第几次、模型、状态、网关任务编号、账本编号、估算花费、失败原因、父结果 |
| `results` | 候选图 | 所属任务与批准、第几轮第几张、图片、父结果、还原度与风格两项验收、问题标签、说明、导出记录 |
| `scenes` | 摄影布景 | 名称、背景、光线、道具、布局、版本历史 |
| `shopStyle` | 我的风格 | 长期偏好、变更记录（每次变更都由用户同意） |
| `events` | 试用事件 | 时间、类型、所属作品、少量数字或短文本（不存整段聊天和原图，AC-10.4） |

关键规则：

- **商品信息每个字段带状态**：已确认／待确认建议／未知。小间写入的只能是「待确认建议」（PRD 4.2 第 3 条）。
- **共创总结带状态**：草稿／已确认。小间只能写草稿，确认由用户点。
- **原图不可覆盖**：替换原图是新增一条记录，旧记录保留（PRD 4.2 第 5 条）。
- 数据表带版本号，以后改结构用 Dexie 的升级函数迁移，不丢旧数据。只加不建索引的可选字段（如 2026-11-01 加的 `revision`、`parentResultId`）不需要升级版本，读的时候把缺省当作没有。
- 修改结果（验收、问题标签、说明、导出记录）用 `patchResult` 按数据库里的最新记录只改对应字段，连着点也不会互相覆盖。
- 2026-11-01 新加的可选字段（不建索引，不升级版本）：作品 `followups`（记下的后续需求）、`proposals`（提议卡片上用户的决定，按工具调用编号）；结果 `thumbId`（缩略图，早期结果没有就用原图）、`published`（商家说已经拿去发布的时间）；任务 `whiteAssetId`（白底任务存下的白底图）。

## 5. 方案、提示词与批准（核心规则）

按发起人决定（PRD AC-07.2a），**最终提示词全部由小间撰写**：

1. **提示词依据**：商品信息（已确认部分）、共创总结（已确认）、风格卡、比例、生图模型、所选资产。代码对这些内容算一个「依据指纹」。
2. **小间写提示词**：调用 `draft_prompt` 工具，写入提示词原文和当时的依据指纹。系统指令要求它写清：主体描述、不能改的细节、只保留原图看得到的结构（不加扣头和链条）、完整入框留边距、无文字，再加上氛围描写。
3. **过期**：当前依据指纹和提示词记录的不一致时，界面标「提示词可能过期」，批准按钮不可用，小间会主动提出重写；用户也可以对照改动后点「我核对过，仍然适用」，依据更新为当前（小间不可用时也能继续，AC-11.6）。
4. **用户可以直接改提示词**（同步做法 2026-10-31 确认，落实 AC-07.2）：改后标「已手动修改」，状态记为「未核对」，小间读一遍改动：
   - 能对应到方案卡的写回方案卡；写回后把提示词记录的依据指纹更新为新状态，避免把用户刚改的提示词判成过期。
   - 对不上的列为「待你决定」，状态记为「有矛盾」。
   - 「未核对」「有矛盾」时批准按钮不可用（由代码判断）。小间同步失败或不可用时如实提示；用户可在画布上并排核对方案与提示词后手动标「已核对」，或撤销手改（AC-11.6：没有模型也能完成确认）。
5. **批准**：只能由界面上的「批准」操作产生（滑动确认组件）。批准记录保存一份快照：资产编号、路线、商品信息、共创总结、风格卡、比例、生图模型、提示词原文、候选数量 2。
6. **批准是否有效**：当前快照与批准快照逐项比对，任一项不同即失效，并列出改了哪几项（参照 v2 原型 `snapshotOf`、`diffSnapshot`）。
7. **生成**：只有存在有效批准才能提交；提交时带上批准编号，按快照里的提示词和资产生成。生成中锁定方案：风格、布景、比例、提示词、生图模型、商品核心信息、共创总结、资产都不能改（画布禁用，小间相应工具拒绝）；售价、目标顾客不在快照里，随时可改。
8. **从指定版本修改**（AC-09.4，`domain/work.ts` 的 `reviseFrom`／`cancelRevision`）：从某张结果开始修改时，恢复那一版批准时的风格、布景、比例、生图模型和提示词；商品信息、共创总结和照片是作品本身的事实，保持现在的（之后改过的话，恢复的提示词会被判为过期）。作品上记下 `revision`（从哪张、当时指出的问题、修改前的方案）；批准时把父结果写进批准记录，新一轮的任务和结果都记父结果，界面显示「改自第 N 轮候选 M」；开始生成后 `revision` 清掉。「取消修改」恢复修改前的方案（连着从几张修改时回到最初）。

## 6. 小间（对话 Agent）

**接口**：`POST /api/chat`

- 请求体：对话消息 + 当前作品状态摘要（由浏览器在每次发送时附带）+ 所选对话模型。
- 服务端：`streamText`，`instructions` 为系统指令（固定规则 + 作品状态摘要），`tools` 为工具定义（只有参数格式，没有执行代码，所以每次请求只走一步），调用前按估价在账本预留，`onEnd` 里按实际 token 结算。
- 商品照片：模型能看图时，每次请求附上当前在用的原图缩略图（长边 768 像素；A 路线再加选定的白底图），最多 6 张；不能看图的模型不发照片，状态摘要里写明。
- 浏览器：`useChat`，在 `onToolCall` 里执行工具并用 `addToolOutput` 交回结果；`sendAutomaticallyWhen` 在工具结果齐了时自动继续，单轮最多自动续 `BUDGET.chat.maxSteps`（8）次，到上限停下并在对话里说明。

**工具清单**（对应 PRD AC-11.2；★ 表示只能「提议」，由用户在卡片上确认；2026-11-01 检查点 6 后全部已接，每个工具的硬规则有单元测试）：

**硬规则在哪里保证**：在浏览器的工具执行器里检查，违反时不执行，并把原因作为工具结果返回给模型，让它向用户解释（AC-11.5）。批准、确认总结、同意保存布景或风格，这些操作只存在于界面按钮里，没有对应的工具。

**推荐怎么落地**（开发时对 AC-05.1、硬规则 3 的落实方式，未请发起人逐项确认）：商品信息只能写「待确认建议」、共创总结只能写「草稿」，都要用户点了才生效；风格卡的推荐（`set_style` 的 `basis: 'recommend'`）直接写进风格卡，标「小间推荐」和理由，批准方案时视为确认，用户随时可在画布上改。

**小间什么时候说话**：只在用户发消息、或点画布上「让小间写／重写／核对／重新整理」「告诉小间哪里不对」时回应。生成完成、确认资产或总结、验收这些画布上的事不会通知小间，它不会自己开口；回访时也不会主动打招呼。这是 AC-11.3、AC-01.2 的缺口；自动开口每次都是一次真实对话调用，要不要做、在哪些节点做，待发起人决定。

**失败处理**：模型调用失败或超时，对话里显示真实错误和「重试」按钮（有次数上限），不用固定话术冒充回复；画布照常可编辑（AC-11.6）。超时：`streamText` 的 `timeout`，首字 75 秒、整轮 150 秒（`config/budget.ts`，本机网络慢时一轮要 14—70 秒，留了余量），超时如实报错、可重试。

**切换模型**（AC-08.7、AC-11.8）：对话框里的输入组件（Prompt Bar）放两个模型选择器，分别选对话模型和生图模型，清单来自 `/api/config`。对话模型默认 `qwen3.8-flash`（能看图、能调用工具），可切换 `deepseek-v4-flash-vision-exp`（`deepseek-v4-flash` 带图会 404，2026-11-01 实测）。现状：已实现（`components/chat/composer.tsx`，用 Prompt Bar）；生成中不能换生图模型；小间只在用户要求时用 `set_image_model`。

**假对话模型**（开发和自动化测试用，`server/fake-chat.ts`）：`FAKE_CHAT=1` 时对话接口不调用模型、不花钱、不记账，按用户最后一句里的「【测试：信息】」「【测试：总结】」等标记照剧本调用工具（剧本见 `FAKE_SCRIPT`，单元测试保证每条都符合工具参数格式）；没有标记时回复写明「测试对话模型，不是 AI」。顶栏标「测试模式」，回复下方标「由 测试对话（不是 AI） 回复」。生产环境即使设了也不生效。

## 7. 生图

**接口**：`POST /api/images` 提交，`GET /api/images/[id]` 查询。

- 网关：AIHubMix 统一生图接口 `/ai/v1/images/generations`，异步模式（账户已开通）。
- 每次生成提交**两个独立任务**（各出 1 张），一张失败不影响另一张，可单独补齐（AC-08.5）。
- 参考图：B 路线用已确认的原图（不超过模型上限）；A 路线用白底图加细节图。
- 服务端拿到结果后立刻下载，交回浏览器存进 IndexedDB（网关的结果只保留 1 小时，最多下载 3 次）。图片已经生成就已扣费，取回时遇到临时错误（断网、网关 5xx）最多再试 3 次（`config/budget.ts` 的 `GENERATION.downloadTries`），仍失败时如实写「生成好了，但取回或保存图片失败」，由商家决定是否补齐。
- 状态如实显示：排队中、生成中、成功、失败；没有进度百分比就不显示（AC-08.4）。
- 已知限制：等 10 分钟没结果判失败（`GENERATION.timeoutMs`）；网关之后若完成仍会扣费，结果拿不回来。（2026-11-01 核查时列出的另外 4 条——任务恢复只在工作区、两个标签页重复存结果、参考图不重新编码、结果没有缩略图——已在检查点 7 修掉。）
- 模型参数差异（Gemini 用 `aspect_ratio`，GPT、Qwen 用 `size`，Seedream 默认出 2048 像素等）集中写在 `config/models.ts`。
- 白底图比较两种做法（PRD 4.3）：①生图模型加白底提示词，走同一个接口；②保留原像素的抠图，发起人曾选定阿里云「商品分割」，后指示先不接。见本节「白底图的两种做法」。
- **假生图网关**（开发和自动化测试用，`server/fake-images.tsx`）：`FAKE_GATEWAY=1 npm run dev` 时三个生图接口不调用模型、不花钱、不记账，几秒后返回写着「TEST IMAGE · NOT AI GENERATED」的测试图，`/api/config` 返回 `fake: true`，顶栏标「测试网关 · 图片非 AI 生成」（AC-08.6）。提示词里带「【测试：失败一张】」时同一段提示词第一次提交的那张失败，带「【测试：全部失败】」时每张都失败，用来测部分失败、补齐和次数上限。生产环境（`NODE_ENV=production`）即使设了也不生效。任务存在 `globalThis` 上，热更新和各接口各自加载模块时也共用。

### 白底图的两种做法（PRD 4.3、AC-02.2、AC-02.3）

A 路线（先白底再生成）需要白底图。两种做法都做，结果都存成派生素材（`assets.origin = 'white'`，`method` 记做法，`parentId` 记原图）；商家对照原图选用一张（`work.whiteChoice`），再确认资产。原图永远不动。

| | ① 生图模型出白底 | ② 抠图（保留原像素） |
| --- | --- | --- |
| 服务 | AIHubMix 统一生图接口，同一个密钥 | 阿里云视觉智能开放平台「商品分割」`SegmentCommodity`（2026-11-01 发起人选定） |
| 做法 | 原图作参考图，加固定的白底提示词（写在配置里），生成一张 | 原图压缩后发给服务端，服务端调阿里云拿回带透明通道的 PNG，浏览器里铺到纯白底上 |
| 花费 | 按所选生图模型的单张价（Seedream 约 0.034 美元） | 0.002 元／次（每月 1 万次以内），调用失败不收费 |
| 风险 | 会重画像素：初测 6 张有 5 张没完整入框，还可能改结构 | 细链、镂空、透明材质可能抠不干净；要发起人开阿里云账号 |
| 状态 | **已做**（2026-11-01 检查点 5） | **暂不接**：发起人 2026-11-01 指示「抠图模型先不接，之后定」，下面的阿里云方案保留备用 |

**② 阿里云商品分割：接口事实**（官方文档，2026-11-01 核实：[接口说明](https://help.aliyun.com/zh/viapi/developer-reference/api-i8iw3k)、[SDK 示例](https://help.aliyun.com/zh/viapi/use-cases/products-division-1)、[计费](https://help.aliyun.com/zh/viapi/product-overview/billing-is-introduced-1)）

- 接口 `SegmentCommodity`，API 版本 2019-12-30，地址 `imageseg.cn-shanghai.aliyuncs.com`。识别商品轮廓、和背景分开，返回前景商品图；适用于实景照片、拍到全貌的商品，不适用卡通图。
- 参数 `ImageURL`（必填，建议上海地域 OSS 地址；本地文件用 SDK 的 Advance 方法直接传文件流）；`ReturnForm`（选填）：不填返回四通道 PNG，`mask` 返回单通道遮罩，`whiteBK` 返回白底图，`crop` 返回裁掉空白边的四通道 PNG。
- 图片要求：JPEG、JPG、PNG（不支持 8 位、16 位、64 位 PNG）、BMP；不超过 3 MB；分辨率小于 2000×2000；URL 不能含中文。
- 返回 `Data.ImageURL`，**30 分钟内有效**，要立刻下载存好。
- 计费：按量 0.0020 元／次（每月 1 万次以内，5 QPS），1 万—500 万次 0.0018 元，以上 0.0016 元；调用失败不收费；没有列出免费额度；欠费 24 小时后冻结调用。
- Node.js SDK：`@alicloud/imageseg20191230`、`@alicloud/openapi-client`、`@alicloud/tea-util`；`segmentCommodityAdvance(request, runtime)`，本地文件放进 `SegmentCommodityAdvanceRequest.imageURLObject`；结果在 `response.body.data.imageURL`。
- 凭据：用 RAM 子账号，授权 `AliyunVIAPIFullAccess`；AccessKey 放环境变量 `ALIBABA_CLOUD_ACCESS_KEY_ID`、`ALIBABA_CLOUD_ACCESS_KEY_SECRET`，不写进代码。

**② 发起人要做的事**（开户、实名、充值属于发起人本人操作）：

1. 注册阿里云（中国站 aliyun.com，需实名）。
2. 在视觉智能开放平台开通「分割抠图」（具体开通入口以控制台为准）。

**① 实际做法**（2026-11-01 检查点 5 已实现）：

- `config/white.ts`：固定白底提示词（完整入框、不改结构、纯白背景、不加文字，带上「不能改的细节」）、比例 1:1、每张原图最多做 3 次（含失败）。
- `domain/white.ts`：`whiteCheck`（只在 A 路线、只给在用的整体或背面原图做；生成中、同一张正在做、次数到上限时拒绝）、`whitesOf`、`makingWhite`；有单元测试。原图停用后，从它做出的白底图不再进参考图（`referencesOf`）。
- `client/generation.ts` 的 `makeWhiteByGeneration`：建 `kind: 'white'` 的任务，和场景图共用提交、轮询、取回重试；完成后存成 `method: 'generate'` 的白底图（记 `parentId`），任务记 `whiteAssetId`。花费照常累加进作品。白底任务不算「生成中」，不锁方案；但做白底时不能删作品。

**② 代码怎么写**（备用方案，暂不接；做法①、路线开关、白底任务、作品状态摘要里的路线都已经有了，下面只列接抠图时要新写的）：

## 12. 凭据统一管理与协作者转发（v0.5，2026-11-01 已确认并实现）

依据：发起人 2026-11-01 选定的《服务端与 API 密钥统一管理方案》（发起人本机文件，不在仓库）和同日的两项选择（agents.md「API 密钥与调用权限」）。后台一侧见 `管理后台/prd/PRD.md` v1.1 和 `管理后台/prd/技术方案.md`。本节写主产品这边的做法；代码已实现（2026-11-01），验证见 `管理后台/prd/验收记录.md`「v1.1」。部署未做。

### 12.1 已定的做法

- AIHubMix key 在管理后台录入，加密后存进服务器上的凭据文件；主产品只读这个文件，自己不提供任何写 key 的接口。
- 一套 key 所有人共用：商家通过网站用；协作者本地开发时，把发往 AIHubMix 的请求转给服务器（12.5），真 key 不离开服务器。
- 后台和主产品放在同一台香港服务器上，后台只监听服务器本机，发起人经 SSH 隧道打开。
- 真实用户的护栏（身份、个人额度、频率）由发起人以后安排，本节不做（限制见 12.8）。

### 12.2 凭据来源

`CREDENTIAL_SOURCE` 在启动时读取，改了要重启；三种来源互不回退。

| 取值 | 用在哪 | 怎么取 key |
| --- | --- | --- |
| `env`（不设时的默认值） | 现在的本地开发 | `.env.local` 的 `AIHUBMIX_API_KEY`，和现在一样 |
| `file` | 香港服务器 | 读 `CREDENTIALS_PATH` 指向的凭据文件，用 `CREDENTIALS_MASTER_KEY` 解密 |
| `relay` | 协作者本地 | 不拿真 key：请求发到 `MODEL_RELAY_URL`（只填服务器地址，路径由代码按供应商拼上），带团队口令 `MODEL_RELAY_TOKEN` |

- `file` 模式下文件缺失、损坏、解密失败或已停用时，给出可读原因并拒绝调用，不改用环境变量。
- 每次调用都重新读凭据文件（文件很小），后台一改，下一个请求就用新的，不用重启。对话和生图现在本来就是每次请求现取 key（AI SDK 的 `apiKey` 传的是函数），只要换掉取 key 的函数。
- 改动点：`src/server/env.ts` 的 `apiKey()` 换成新文件 `src/server/credentials.ts`（server-only）里的统一读取；`/api/config` 的「是否已配置」改用同一来源（12.4）。

### 12.3 凭据文件

- 格式和加解密写在 `src/server/credential-file.ts`。它只依赖 `node:crypto`、只用可擦除的 TS 写法，也不引 `server-only`：管理后台要用 Node 直接加载它（和后台现在读 `models.ts` 的方式一样），这样两边只有一份实现。浏览器代码引用它会在打包时报错。
- 算法：AES-256-GCM，每次加密重新生成 12 字节随机 IV；附加数据绑定格式版本和供应商（`yijian-credential:v1:aihubmix`）。主密钥是 32 字节随机数的 base64，长度不对直接报错。
- 内容：`schemaVersion`、`revision`、`updatedAt`；`providers.aihubmix` 存状态（`active`／`disabled`），当前 key 的密文、尾号和保存时间，以及替换时留下的上一把 key（`previous`：密文、尾号、替换时间）；`relay` 存团队口令的 SHA-256 散列、尾号和状态；另有操作记录（时间、动作、尾号）。文件里没有任何明文。
- 只有管理后台写这个文件（原子替换加 revision 校验，见后台技术方案），主产品只读。文件放在仓库之外，比如 `/var/lib/yijian/credentials.json`，目录权限 700、文件 600。

### 12.4 读取规则

- **新请求**（对话、提交生图）：状态必须是 `active`，用当前 key。
- **已提交的生图**（查状态、取图）：AIHubMix 文档写明「任务及内容按创建任务时的 Bearer Token 隔离」，换 key 后，旧任务很可能只有旧 key 才取得到。所以：
  - 停用只拦新请求，不拦查询和取图，免得已经扣费的图拿不回来；
  - 当前 key 查旧任务返回 404（`task_not_found`）时，如果上一把 key 替换还不到 24 小时，改用它再查一次。24 小时写在 `config/credentials.ts`。
- 从 `env` 切到 `file` 时如果换了 key，切换前提交的任务同样可能取不回，所以切换要选在没人生图的时候。
- `/api/config` 返回 `credential: { source, ready, revision, reason }`，不含尾号和密钥；原有的 `configured` 保留，值等于 `ready`。后台用 `revision` 核对主产品读到的是不是同一份文件。

### 12.5 协作者转发

**服务器一侧**：新接口 `/api/relay/aihubmix/[...path]`。只在 `file` 模式、而且后台生成过团队口令时开放，否则返回 404。

- 校验 `Authorization: Bearer <团队口令>`：算散列后用定长比较。
- 只放行 4 个转发路径：`POST v1/chat/completions`、`POST ai/v1/images/generations`、`GET ai/v1/images/{id}`、`GET ai/v1/images/{id}/content/{result_id}`，编号按格式校验；另加 `GET status`，告诉协作者本地服务器这边能不能用。其余路径一律 404。上游只发往 `GATEWAY` 里的固定域名。
- 模型必须在服务器的 `config/models.ts` 里，规则同 `/api/chat`、`/api/images`。沿用 `budget.ts` 的单张估价上限和总预算，记进服务器账本，条目加 `via: 'relay'`。对话按请求字数和输出上限预留估价，流结束时按返回的用量结算，拿不到用量就按估价记（宁多勿少，同现有规则）。
- 流式回复原样转回；上游的错误文字先脱敏（12.6）再返回。不记录请求内容，里面有照片和对话。

**协作者本地**（`relay` 模式）：

- `aihubmix.ts` 的两个网关地址换成服务器地址（`MODEL_RELAY_URL`）加 `/api/relay/aihubmix` 下对应的路径，凭据换成团队口令；`MODEL_RELAY_URL` 带了路径会直接报错，不拼成两层；结果下载地址 `content_url` 是网关域名，换成转发地址后再取。
- 小间的系统规则、工具、模型选择都在协作者本地执行，所以协作者改的代码能用真实模型测到；只有发往 AIHubMix 的那一步经过服务器。
- `/api/config` 在 `relay` 模式下请求服务器的 `status`（短超时），如实显示服务器那边能不能用。
- `/api/images` 收到服务器回的 `not_configured`（服务器的 key 没配好或已停用）时退回本地预留：请求没有发到 AIHubMix（联调时发现后补上）。

### 12.6 脱敏

错误文字返回浏览器或写进日志之前，先把当前 key、上一把 key、团队口令的原文换成「尾号 xxxx」，再把 `sk-` 开头的长串整体替换掉。

### 12.7 部署要点（补充交接文档第 10 节）

- 主产品和后台用同一个系统用户运行，共用一份环境变量文件（权限 600），写 `CREDENTIAL_SOURCE=file`、`CREDENTIALS_PATH`、`CREDENTIALS_MASTER_KEY`；服务器上不再放 `AIHUBMIX_API_KEY`。服务器第一次部署就用 `file` 模式（服务器上没有旧的环境变量要迁移）。发起人定（2026-11-01）：正式上线前本地开发照旧用 `env`；上线后本地开发一律走 `relay`，用后台管理的那套 key。
- 主产品 `next start` 只监听 127.0.0.1，经 HTTPS 反向代理对外；后台不经反向代理。反向代理的请求体上限要放大（nginx 默认只收 1MB），至少容纳 8 张 2048px 参考图的 base64（`config/upload.ts`），具体值部署时实测。现有的 `/api/images` 也需要这一条。
- 主密钥单独备份（比如放密码管理器），不和凭据文件放在一起。主密钥丢了也能恢复：在 AIHubMix 重新生成 key，到后台重新录入。
- 服务器地址和团队口令都不进公开仓库，私下发给协作者，写进各自的 `.env.local`。

### 12.8 已知限制（发起人已知悉的取舍）

- 真实用户的护栏做好之前，网站自己的 `/api/chat`、`/api/images` 对知道网址的人仍是开放的；团队口令只管转发入口。兜底靠 AIHubMix key 的额度和服务器账本的总预算。
- 一套 key、一个团队口令：AIHubMix 和账本只分得出「网站」和「转发」，分不出是哪位协作者花的。某位协作者退出时只能换口令，其他人也要跟着换新的。
- 换团队口令后，协作者进行中的生图会取不回。
- 后台没有账号，SSH 就是门槛；操作记录里不区分是谁。

### 12.11 以后增加供应商

发起人 2026-11-01：供应商（发 key 的平台）目前只有 AIHubMix，以后可能加别的平台，可能是模型出品方的官方接口，也可能是别的中转。现在不做，记下要改的地方。

- 已经按供应商分开的：凭据文件按供应商存（`providers.<供应商>`，加密附加数据也绑定供应商）；转发路径带供应商（`/api/relay/aihubmix/…`）；后台凭据表每行显示模型所属的供应商。
- 模型配置：每个模型要写明走哪个供应商、在该供应商那里的 API ID 和价格。同一个模型走不同供应商时名字和价格可能不同，算两条。
- 网关：对话大多是 OpenAI 兼容接口，换地址和 key 就行；生图各家协议不同（AIHubMix 用的是它自己的异步任务接口），每家要单独写一套，这是加供应商的主要工作量。
- 凭据：`credential-file.ts` 的 `PROVIDER_IDS` 加一项。像阿里云这样要两项凭据（AccessKey ID 和 Secret）的，凭据文件要升一版格式，后台表单也要两个输入框。
- 状态：`/api/config` 和后台的「主产品当前读取」改成按供应商分别报；转发按供应商分路径，各自一份模型白名单。
- 协作者的 `MODEL_RELAY_URL`：已改为只填服务器地址（发起人 2026-11-01 定），代码按供应商拼 `/api/relay/<供应商>`，加供应商时协作者不用改配置。
