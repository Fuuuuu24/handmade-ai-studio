## 2. 总体结构

```text
浏览器（界面＋本地数据）                          服务端（Next.js 接口，只做代理）            AIHubMix
┌───────────────────────────────┐   POST /api/chat     ┌──────────────────────────┐   对话模型
│ 页面：首页／作品／工作区／风格／布景／历史 │ ───────────────────▶ │ 小间：streamText＋工具定义  │ ─────────▶
│ 工作区：左对话（useChat）右画布      │ ◀─── 流式回复＋工具调用 │ 记账：按 token 计费        │
│ 工具执行器：小间的工具在浏览器里执行   │                      └──────────────────────────┘
│ 规则层：批准、快照、状态机（纯函数）   │   POST /api/images   ┌──────────────────────────┐   生图模型
│ 存储：IndexedDB（作品、图片、对话）    │ ───────────────────▶ │ 提交任务、查询、下载        │ ─────────▶
└───────────────────────────────┘ ◀─── 任务状态／图片   │ 预算与重试上限检查          │
                                                     └──────────────────────────┘
```

- **数据都在浏览器**（PRD O5）。服务端不存作品和照片，只转发请求，并记一本花费账。
- **密钥只在服务端**：`正式代码/.env.local` 里的 `AIHUBMIX_API_KEY`，不进版本库，也不发给浏览器。
- **小间的工具在浏览器执行**：模型决定调用哪个工具，工具的执行代码在浏览器里运行并修改本地数据。这样服务端不需要保存作品状态。
- **不设访问限制**（2026-10-31 发起人决定）：试用网址不加邀请码或密码，发起人判断不会有外人使用；花费由服务端的预算上限兜底。
- **硬规则的保证范围**：批准与生成前的检查在浏览器的规则层和工具执行器里做，能挡住模型绕过规则；服务端不存作品，无法校验批准，只负责预算和重试上限。改浏览器代码的人挡不住，试用期可接受。
- **花费按作品记录**：服务端每次调用算出花费，随响应返回；浏览器记在对应的生成任务和对话上，试用记录据此统计每人累计成本（PRD 6.2 记录模板）。

├─ tests/e2e/                      # Playwright

约定：

- `domain/` 只放规则，凡是「能不能批准」「批准是否失效」「作品处于哪个状态」都在这里判断，界面和小间都调用同一份。
- `server/` 下的文件只在服务端导入，开头加 `import 'server-only'` 防止误打包到浏览器。
- 所有可调的数字（预算、重试次数、上传大小、超时）只写在 `config/`。

## 4. 数据模型（IndexedDB）

| 表 | 内容 | 关键字段 |
| --- | --- | --- |
| `works` | 作品 | 名称、创建／更新时间、商品信息、共创、风格卡、比例、所选生图模型、资产路线 A/B、提示词、批准记录 |
| `assets` | 商品照片与派生图 | 所属作品、类型（整体／背面／细节／白底）、来源（上传／派生，派生图记父图）、确认状态 |
| `blobs` | 图片二进制 | 原图、白底图、生成图都存这里，其他表只存编号 |
| `messages` | 对话 | 所属作品、AI SDK 的 UI 消息原样保存（含工具调用记录，满足 AC-11.4） |
| `tasks` | 生成任务 | 所属作品、所用批准、模型、比例、路线、状态、网关任务编号、估算花费、失败原因 |
| `results` | 候选图 | 所属任务、图片、父结果、还原度与风格两项验收、问题说明、导出记录 |
| `scenes` | 摄影布景 | 名称、背景、光线、道具、布局、版本历史 |
| `shopStyle` | 我的风格 | 长期偏好、变更记录（每次变更都由用户同意） |

关键规则：

- **商品信息每个字段带状态**：已确认／待确认建议／未知。小间写入的只能是「待确认建议」（PRD 4.2 第 3 条）。
- **共创总结带状态**：草稿／已确认。小间只能写草稿，确认由用户点。
- **原图不可覆盖**：替换原图是新增一条记录，旧记录保留（PRD 4.2 第 5 条）。
- 数据表带版本号，以后改结构用 Dexie 的升级函数迁移，不丢旧数据。

## 5. 方案、提示词与批准（核心规则）

按发起人决定（PRD AC-07.2a），**最终提示词全部由小间撰写**：

1. **提示词依据**：商品信息（已确认部分）、共创总结（已确认）、风格卡、比例、生图模型、所选资产。代码对这些内容算一个「依据指纹」。
2. **小间写提示词**：调用 `draft_prompt` 工具，写入提示词原文和当时的依据指纹。系统指令要求它写清：主体描述、不能改的细节、只保留原图看得到的结构（不加扣头和链条）、完整入框留边距、无文字，再加上氛围描写。
3. **过期**：当前依据指纹和提示词记录的不一致时，界面标「提示词可能过期」，批准按钮不可用，小间会主动提出重写。
4. **用户可以直接改提示词**（同步做法 2026-10-31 确认，落实 AC-07.2）：改后标「已手动修改」，状态记为「未核对」，小间读一遍改动：
   - 能对应到方案卡的写回方案卡；写回后把提示词记录的依据指纹更新为新状态，避免把用户刚改的提示词判成过期。
   - 对不上的列为「待你决定」，状态记为「有矛盾」。
   - 「未核对」「有矛盾」时批准按钮不可用（由代码判断）。小间同步失败或不可用时如实提示；用户可在画布上并排核对方案与提示词后手动标「已核对」，或撤销手改（AC-11.6：没有模型也能完成确认）。
5. **批准**：只能由界面上的「批准」操作产生（滑动确认组件）。批准记录保存一份快照：资产编号、路线、商品信息、共创总结、风格卡、比例、生图模型、提示词原文、候选数量 2。
6. **批准是否有效**：当前快照与批准快照逐项比对，任一项不同即失效，并列出改了哪几项（参照 v2 原型 `snapshotOf`、`diffSnapshot`）。
7. **生成**：只有存在有效批准才能提交；提交时带上批准编号，按快照里的提示词和资产生成，生成中锁定方案。

## 6. 小间（对话 Agent）

**接口**：`POST /api/chat`

- 请求体：对话消息 + 当前作品状态摘要（由浏览器在每次发送时附带）+ 所选对话模型。
- 服务端：`streamText`，`instructions` 为系统指令（固定规则 + 作品状态摘要），`tools` 为工具定义（只有参数格式，没有执行代码），`stopWhen: isStepCount(…)` 限制单轮步数，`onEnd` 里按 token 记账。
- 商品照片：每次请求附上已确认资产的缩略图（长边约 768 像素），让小间看得到商品。
- 浏览器：`useChat`，在 `onToolCall` 里执行工具并用 `addToolOutput` 交回结果；`sendAutomaticallyWhen` 设为工具结果齐了自动继续。

**工具清单**（对应 PRD AC-11.2；★ 表示只能「提议」，由用户在卡片上确认）：

| 工具 | 作用 | 硬规则 |
| --- | --- | --- |
| `update_info` | 写商品信息 | 只能写成「待确认建议」 |
| `record_story` | 记录用户讲的灵感、主题、情绪 | — |
| `offer_picks` | 「我不知道」时给出 3 个方向卡片 | — |
| `draft_summary` | 起草三项共创总结 | 只能是草稿，确认由用户点 |
| `set_style` | 改风格卡（色调、背景、光线、摆放、道具、构图、表达） | — |
| `apply_scene` | 套用布景模版或已存布景 | — |
| `set_ratio` / `set_image_model` | 改比例、改生图模型 | 会让旧批准失效 |
| `make_white_asset` | 做白底图（A 路线） | 派生新图，原图保留 |
| `draft_prompt` | 写最终提示词 | 记录依据指纹 |
| `request_approval` | 在对话里放出批准卡片 | 小间不能自己批准 |
| `start_generation` | 提交生成 | 无有效批准时拒绝并返回原因 |
| `retry_candidate` | 补齐失败的一张 | 受重试上限约束 |
| `note_feedback` | 记录用户对候选图的意见 | 两项验收由用户点 |
| `propose_scene_save` ★ | 提议保存为布景 | 用户确认才写入 |
| `propose_shop_style` ★ | 提议更新我的风格 | 用户确认才写入 |
| `show_step` | 让画布切到某一步 | — |

**硬规则在哪里保证**：在浏览器的工具执行器里检查，违反时不执行，并把原因作为工具结果返回给模型，让它向用户解释（AC-11.5）。批准、确认总结、同意保存布景或风格，这些操作只存在于界面按钮里，没有对应的工具。

**失败处理**：模型调用失败或超时，对话里显示真实错误和「重试」按钮（有次数上限），不用固定话术冒充回复；画布照常可编辑（AC-11.6）。

**切换模型**（AC-08.7、AC-11.8）：对话框里的输入组件（Prompt Bar）放两个下拉框，分别选对话模型和生图模型，清单来自 `/api/config`。对话模型默认 `qwen3.8-flash`（能看图、能调用工具），可切换 `deepseek-v4-flash`。

## 7. 生图

**接口**：`POST /api/images` 提交，`GET /api/images/[id]` 查询。

- 网关：AIHubMix 统一生图接口 `/ai/v1/images/generations`，异步模式（账户已开通）。
- 每次生成提交**两个独立任务**（各出 1 张），一张失败不影响另一张，可单独补齐（AC-08.5）。
- 参考图：B 路线用已确认的原图（不超过模型上限）；A 路线用白底图加细节图。
- 服务端拿到结果后立刻下载，交回浏览器存进 IndexedDB（网关的结果只保留 1 小时，最多下载 3 次）。
- 状态如实显示：排队中、生成中、成功、失败；没有进度百分比就不显示（AC-08.4）。
- 模型参数差异（Gemini 用 `aspect_ratio`，GPT、Qwen 用 `size`，Seedream 默认出 2048 像素等）集中写在 `config/models.ts`。
- 白底图比较两种做法（PRD 4.3）：①生图模型加白底提示词，走同一个接口；②保留原像素的抠图（专用服务或开源模型）。两种结果都作为派生素材保存，商家对照原图后确认用哪张。抠图服务的选型在第 10 节第 5 步调研，涉及花钱或开新账号先问发起人。依据：初测里生图模型出的白底 6 张有 5 张没完整入框；抠图保留原像素，但细链、透明材质对抠图同样难，所以要实测比较。

**预算与上限**（PRD 4.2 第 4 条，写在 `config/budget.ts`）：

- 总预算、单次估价上限、每张候选的重试次数上限、对话单轮步数上限。
- 服务端每次调用前按估价记账，超过上限直接拒绝，界面提示「已到预算上限」。
- 账本存在服务端本地文件（试用时在香港服务器上），不在浏览器，防止被改。

- **用户输入一律当文本渲染**，不用 `dangerouslySetInnerHTML`。

## 10. 开发顺序与汇报点

按发起人要求：全部写完再交付，每个检查点只汇报、不停；每个检查点在本地提交一次，方便出问题时回退，不推送、不建 PR。

v0.2 调整（2026-10-31 发起人选择）：先走通一条最细的真实流程，再铺满功能，让生图还原度和小间理解能力这两个最大的未知数尽早暴露（PRD 9.1 对话模型风险的处理方式）。这仍是在产品里测，不是恢复单独摸底。

1. 数据层与规则层（先写测试）：类型、快照与差异、批准、状态、依据指纹、冲突检测；IndexedDB 表结构；配置。
2. **最细真实流程**：最简工作区（上传一张照片、对话、方案、批准、两张候选），接真实对话模型（少量工具）和真实生图，用一张真实饰品照片走通；花费控制在 1–2 美元以内，从现有余额支出。
3. 外框与样式：图标栏、顶栏、首页、作品页，迁移视觉规范。
