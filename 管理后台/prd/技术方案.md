# 独立后台技术方案

## 已确认的实现边界

在项目根目录下独立建设；允许只读主产品配置，禁止写回。采用已提议的本地 Node.js 小站：Node 24 原生 HTTP 服务 + HTML/CSS/JavaScript，无新增依赖。后台规模只有提示词和模型配置，不复制主产品的 Next.js 构建链，也不启动主产品。

v1.1（用户确认，2026-11-01 已实现）：后台可以写服务器上的凭据文件，而且只写这一个文件；为此在用到时加载主产品的 `正式代码/src/server/credential-file.ts`（格式与加解密，两边共用一份）和 `正式代码/src/config/credentials.ts`（上一把 key 的保留时长），读不到只让凭据页报错。仍不写主产品源码与配置、不调模型。后台与主产品同机部署在香港服务器，只监听 127.0.0.1（部署另行授权）。

## 数据与同步

只读路径固定为 `正式代码/src/agent/instructions.ts`、`正式代码/src/config/white.ts`、`正式代码/src/config/models.ts`。利用 Node 24 的 TypeScript 类型剥离加载无副作用的配置模块，以内容摘要作为模块缓存键；导入失败即报告。白底提示词从实际 `WHITE.prompt` 生成保真变量标记，不手抄另一份模板。

`管理后台/正式代码/data/state.json` 独立存储 schemaVersion、revision、来源快照、后台提示词和模型、默认模型及修改记录。写入临时文件后原子替换；所有写操作排队，采用 revision 乐观锁避免多标签页互相覆盖。数据文件不入库。原型单独使用 localStorage。

同步先读取并预览，再按文件摘要校验后应用：后台项未修改则跟随最新来源；已修改则保留，更新基准并标记分歧；新增后台项保留。来源删除的项不物理删除。后台禁用、默认值等独有字段保留。

## 凭据（v1.1）

主产品一侧的读取规则、文件格式和转发见 `docs/tech-design.md` 第 12 节，这里只写后台怎么写。

- 位置与主密钥：读环境变量 `CREDENTIALS_PATH`（绝对路径，放在仓库之外）和 `CREDENTIALS_MASTER_KEY`，和主产品用同一份环境变量文件。缺了任何一个，页面显示「未设置」，写入接口拒绝。
- 新模块 `正式代码/credentials.mjs`：加载主产品的 `credential-file.ts` 做加解密和格式校验；写入走串行队列，用凭据文件自己的 revision 做乐观锁，写同目录临时文件后原子替换，文件权限 600。先校验再写，坏文件报错，不覆盖、不重置。
- key 的输入：去掉首尾空白，长度 16—256，不能含空白和控制字符，不强制 `sk-` 前缀。替换时把当前 key 移到 `previous`（覆盖更早的那把），记下替换时间。
- 团队口令：`crypto.randomBytes(32)` 转 base64url；文件里只存 SHA-256 散列和尾号，原文只在生成或更换那一次的响应里返回。
- 操作记录写在凭据文件里，和写入是同一次原子替换，保留最近 200 条；「修改记录」页把后台记录和凭据记录合在一起按时间显示。
- 读取状态时在内存里试解密一次，用来发现主密钥不对或密文被改；明文不离开这个函数。
- 主产品当前读取：后台服务端请求 `PRODUCT_INTERNAL_URL`（默认 `http://127.0.0.1:3000`）的 `/api/config`，取其中的 `credential`，超时 3 秒；失败时如实显示「主产品没运行或连不上」。

## 接口

- `GET /api/state`：读取后台当前数据，首次自动从来源初始化。
- `GET /api/source`：只读取得当前来源快照供预览。
- `POST /api/action`：带 revision 执行提示词保存/恢复、模型保存/启停/默认、单向同步。
- `GET /api/export`：导出后台 JSON，不含凭据。
- `GET /api/credentials`（v1.1）：凭据状态（不含原文和密文）和主产品的读取状态。
- `POST /api/credentials`（v1.1）：带凭据文件 revision 执行 `key.set`（配置或替换）、`key.disable`、`key.enable`、`relay.create`、`relay.rotate`、`relay.disable`；请求体上限 8 KB。

所有写请求要求同源 JSON，限制请求体大小，凭据接口沿用同样的 Host、Origin、JSON 检查；服务只绑定 127.0.0.1，静态文件使用显式白名单，不提供任意文件读取或写入。校验失败用 400，版本冲突用 409，来源读取失败用 500，错误原样以可读内容显示。不读环境文件、不调真实网关；key 只经 `POST /api/credentials` 写入，任何响应、日志和导出都不含原文或密文，错误信息不回显输入。

## 界面

沿用用户指定 CBI Admin 的浅灰画布、白色面板、左侧分组导航与表格。结合一间的克制密度：13px 正文、24px 页面标题、细边框、柔和圆角；紫色作当前导航、黄绿色作关键保存动作。提示词采用专门的宽编辑区，模型详情在独立编辑页呈现，不以小卡片挤压长文本。「供应商与凭据」页（v1.1）用表单加确认弹窗：key 输入框为密码框，保存后清空；团队口令的原文只在生成后的弹窗里显示一次，关掉就再也看不到。

## 部署（v1.1，同机，经 SSH 隧道）

- 服务器上和主产品用同一个系统用户运行：`ADMIN_PORT=4177 node server.mjs`，只监听 127.0.0.1，不经反向代理，不对外开放端口。
- 后台照旧从服务器上的仓库副本只读同步主产品配置。
- 发起人打开方式：新增 `npm run remote`，读本机不入库的 `ADMIN_SSH_HOST`，执行 `ssh -N -L 4177:127.0.0.1:4177 <主机>`，再打开 `http://127.0.0.1:4177`。隧道两端端口必须相同，因为后台只接受 Host 为 `127.0.0.1:<监听端口>` 的请求。用隧道时本机不要同时开本地后台，端口会冲突。
- 服务器地址不写进仓库（仓库是公开的）。

## 验证上限

阶段性代码检查与 Node 原生集成测试；浏览器两轮上限（初检、一次集中修复后的复检）。验证单向同步、草稿保留、保存持久化、模型约束、版本冲突，以及屏幕里的关键操作。所有测试使用后台自己的临时数据，清理本轮临时测试目录；交付保留原型、正式代码、截图和文档。

v1.1 另验证：加解密往返；主密钥错误、密文被改时报错；坏文件不被覆盖；版本冲突 409；文件权限 600；任何接口和导出都取不回 key；口令原文只返回一次；操作记录里没有明文。凭据测试只用临时目录、临时主密钥和假 key。
